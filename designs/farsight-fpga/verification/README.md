# PolarFire FPGA verification

How the requirements in
[`docs/requirements/pf-fpga-requirements.md`](../docs/requirements/pf-fpga-requirements.md)
earn evidence in simulation, and how to add a test.

The framework this implements is `farsight-verification`:
`docs/plans/verification-framework-plan.md` for the structure, and
`docs/plans/pf-fpga-vv-plan.md` for the clauses this design's items cite
(`VVP-PF-001` simulation, `-003` inspection, `-004`/`-005`/`-007` analysis,
`-006` hardware). This directory is completely separate from the housekeeper's
environment: nothing here imports from, or is imported by, another repository.

The short version: **the item is the specification.** You do not decide what a
test must prove or what to call it -- that is written in
[`items.yaml`](items.yaml), because writing it down is what exposes the
criteria that cannot be met. You implement it.

---

## 1. Find the item

```
grep -B2 -A14 "PF-UDP-04" verification/items.yaml
```

| Field | What it tells you |
| --- | --- |
| `artifact` | the file to write, and the test name inside it |
| `criteria` | what has to be true for it to pass -- the spec |
| `level` | `unit`: one IP block's testbench; `subsystem`: the whole design |
| `requires` | requirements your evidence depends on; `VENV-02` on every SIM item |
| `expect` | `FAIL` when the requirement's status is `GAP`, `AMBIG` or `DEFECT` |

## 2. Write the test at the path the item names

An unwritten SIM item names `test/sim/pf_<area>_tb::test_PF_<AREA>_<n>_...`.
Write the test as a cocotb coroutine of **that name** in
`verification/tests/test_pf_<area>.py`, and change the item's artifact to
`verification/tests/test_pf_<area>.py::<the same name>`. The name is not yours
to choose: JUnit has no field for a requirement, so the test name is the only
channel through which the trace link survives into the result.

A module is a set of cocotb tests plus one pytest function that builds and
runs the DUT:

```python
from fsverif import clkrst, sim

@cocotb.test()
async def test_PF_PPS_07_local_pps_1hz_50pct(dut):
    clkrst.start_clock(dut.clk, 20.0)
    ...

def test_pf_pps():
    sim.run(hdl_toplevel="pps_generator",
            sources=sim.block("pps_ip", "pps_generator.sv"),
            test_module="test_pf_pps",
            parameters={...})          # the synthesis values -- VENV-02
```

`sim.block(name, *files)` resolves our own IP, `ip/<name>/src/<file>`, file by
file. `sim.vendor(*components)` adds generated vendor cores, checked against
their lockfiles, and `sim.polarfire_source()` the PolarFire primitive library
they are built from. `fsverif.bfm.apb.Apb` drives a register interface.

**Where the requirement is about wiring, the DUT is the SmartDesign.** The PPS
tests run on `pps_hier`, generated by `make ip` as the build generates it,
because the mux feeding the discipline input exists only in its wiring. The
top module's own ports and nets are always reachable from a test; nothing
below it is unless named with `internal=`.

**Tests are split into files to run in parallel.** pytest gives each file its
own worker, and a simulated second of the 50 MHz fabric costs about 47 s, so
three files of two long tests finish in the time of the longest.

**Lint does not fail a simulation.** Verilator's lint and style warnings are
off in simulation builds and the rest are non-fatal. Whether a width mismatch
is acceptable is the lint flow's finding to disposition, not a test's.

## 3. Check that it is wired in

```
make test-fast
```

Fails when an item names a test that does not exist, when a `test_PF_*` test
is named by no item, when a test mutes itself, when an item verifies a
requirement the document does not hold, and when `ip.yaml` names a component
the build does not define.

## A test reports what happened

**Never mute a test.** Not `expect_fail`, not `expect_error`, not `skip`, not
`xfail`; `make test-fast` refuses all of them in a `test_pf_*.py` file. If the
requirement is not met, the test fails and stays failing. A known shortfall is
declared on the *item*, with `expect: FAIL` -- a label, not a suppression -- and
`make check` tells the three cases apart:

| | |
| --- | --- |
| fails, `expect: FAIL` declared | known shortfall, still open -- does not block |
| fails, not declared | regression -- blocks |
| passes, `expect: FAIL` declared | fixed; update the item and the requirement status -- blocks |
| skipped | no evidence -- blocks |
| no result at all | the test exists and did not report: it failed to import or start, or its results were not collected -- blocks |

**Passing with a disposition** is recorded in
`verification/requirement-dispositions.yaml` (`fsverif.dispositions`), in two
kinds that say different things and are never merged:

- A **waiver** accepts a requirement as not met. The item keeps `expect: FAIL`
  and the test keeps failing, so the gate is unchanged; the requirement reads
  **waived** instead of failing, with who accepted it. When the design is fixed
  the test passes, the gate calls the item stale, and the waiver goes too.
- An **exception** is an instance the requirement itself permits to differ --
  a register that may go without a reset, say. The test checking the
  requirement calls `dispositions.check(requirement, found)` and fails on any
  instance not listed *and* on any listed one it no longer finds, so the record
  cannot drift from the design. Once its tests pass the requirement reads
  **passing, with exceptions**.

Neither applies until `approved_by` names someone and `date` is set; with
`approved_by: UNASSIGNED` it shows as proposed and changes nothing. `make
test-fast` holds the record to the requirements and items it names.

**A test states its own preconditions** (framework I.6). `VENV-02` requires the
design exercised at its synthesis parameter values: pass them explicitly, and
where a block has a parameter that makes it simulate faster, assert that it is
not being overridden rather than relying on somebody to remember.

## 4. Running

```
make setup          # once: virtualenv at .venv-verif (and Verilator, without root)
make ip             # once: vendor IP for simulation; needs Libero, no synthesis licence
make test           # the suite; make test TEST=test_pf_pps_local for one module,
                    #   TEST='test_pf_pps_*' for several; measures code coverage
                    #   and writes its report -- COV=0 for neither
make test-fast      # the checks that need no simulator, in a second
make check          # whether the results should block a merge
make coverage       # where each requirement stands; SIM=1, GROUP=UDP, TODO=1
make code-coverage  # the code coverage report again, from the data in hand
make gui-web        # the app, in a browser tab -- section 4a
make sarif          # failing tests and unreached lines, for VS Code's SARIF Viewer
make clean          # simulation products, results, coverage
```

If Verilator 5.020 or later is already on your PATH, `make setup
SETUP_ARGS=--skip-verilator`.

**Code coverage is measured on every run** by both simulators: Verilator
instruments its builds (line, branch, expression and toggle) into
`coverage/<run>.dat`, and QuestaSim -- for the modules pinned to it --
compiles with `+cover=sbcet` and saves `coverage/<run>.ucdb`. The two formats
do not merge natively, so `code_coverage.py` combines them per source line
(`fsverif.ucdb`): a line or a toggled bit either simulator reached counts as
reached, in one annotated source per file under `coverage/annotated/`. Every figure
the report and the app show is of this design's own sources only -- not
vendor IP in `verification/ip`, Libero's simulation library or the testbench
-- with each point counted once however many instances or testbenches reached
it (`fsverif.codecov.tally`). The headline is **code lines** (those with a
statement or branch point; a declaration whose only points are toggles is
reported with the toggles) and **toggles**, both merged across the simulators.
Branch, condition and expression points are each simulator's own, so they are
reported per simulator, not added. Verilator's own summary, which counts every
instance of every file simulated and is mostly testbench and vendor models, is
printed for reference and is not the coverage of this design. Instrumentation makes a run several times slower; `COV=0` (or
`FSVERIF_COVERAGE=0`) skips it for a quick rerun. Not `COVERAGE=0`: cocotb
reads `COVERAGE` as "measure the testbench's own Python".

**Nothing is shared with another checkout.** `make setup` puts every tool it
installs inside this one: the virtualenv at `.venv-verif`, and micromamba, its
package cache, the Verilator environment and pip's cache under `.tools/`.
micromamba and pip read no per-user configuration. The Python that Verilator's
build runs is linked from `sim_build/` (`fsverif.sim._python_shim`), and the
Libero IP vault `make ip` generates from is `.tools/vault` (section 5). A tool
under `$HOME` is one another checkout's setup can upgrade or rewrite under
this one, and one did: a shared environment's Python moved to 3.14 and a
shared shim was relinked, and every Verilator build here broke.

## 4a. Reviewing a run: the app

```
make gui-web
```

It prints an address with a token -- `http://127.0.0.1:8765/?token=...` --
and VS Code forwards the port by itself. Open it with **Ctrl+Shift+P, "Simple
Browser: Show"** and paste the address, or Ctrl+click it for a browser outside
VS Code. Ctrl+C in the terminal stops it; `FSVERIF_PORT` picks another port.
It needs nothing beyond `make setup`, and it listens only on this machine: the
token is what stops anybody else logged in to a shared machine from starting
runs as you. Start it from a VS Code terminal and **Open source** opens files
in that VS Code window.

It shows every requirement test -- simulations and analyses alike -- with what
it did and the gate's verdict beside it, the requirements and findings behind
them, and code coverage. A simulation's detail shows the values it logged
(`fsverif.runlog` keeps each run's log as `results/log-<run>.txt`); an
analysis's shows its recorded calculation. Runs can be started, followed and
cancelled from it, and a run made from a terminal is picked up on its own.
Verdicts and requirement stages come from the same code as `make check` and
`make coverage` (`check_results.classify`, `evidence.stage`), so the app cannot
disagree with them.

**Traceability** lists every Jama requirement the PolarFire answers to
(`docs/requirements/jama.yaml`): the 20 FAR-CDH_FPGA L3 requirements allocated
to it, and every other Jama requirement an FPGA requirement cites as its
parent. Each is judged by the PF requirements under it: **passing** when every
one is, **failing** when any has a failing test, **partly tested** when any has
no test or no result yet, **waived** when the worst is a shortfall an approved
waiver accepts, **verified elsewhere** when none cites it
but its snapshot entry has a hand-written `verified_in:` (it is allocated to the
PolarFire firmware, whose requirements are in `farsight-avionics-sw`, not here),
and **no local requirement** when nothing cites it. Its detail
gives the Jama wording, and each requirement under it with its tests, their
results and its findings. The Requirements page gains a Jama-parent filter and
column, and Jama identifiers are links everywhere.

The Jama snapshot is refreshed from a Jama trace-view CSV export -- the one in
hand is `farsight-verification/docs/requirements/Farsight.csv` -- with
`../.venv-verif/bin/python -m fsverif.jama --csv <export.csv>`, run in
`verification/`. It keeps each entry's hand-written `note:` and `verified_in:`,
and refuses a text with a mangled character it cannot account for: the export
turns ≥ and ≤ into "?", and `fsverif.jama.SYMBOL_FIXES` holds the ones confirmed against Jama.
`make test-fast` checks that every parent a requirement cites is in the
snapshot.

## 4b. In CI

`.gitlab-ci.yml` runs three jobs on a merge request:

| Job | Runner | What it does |
| --- | --- | --- |
| `fast-checks` | any (`python:3.12`) | `make test-fast`'s checks: every item names a test that exists, no test mutes itself, the app reads the documents, every cited Jama parent is in the snapshot |
| `verify` | tagged `libero` | an FPGA build, `setup-tools.sh`, the vendor IP (`make ip`, cached), then `make test` -- every simulation, analysis and inspection, with code coverage. Allowed to fail: evidence, not a verdict |
| `gate` | any | `check_results.py` on `verify`'s results: blocks on a new failure, a stale `expect: FAIL`, a skip, or a written test with no result -- never on a declared shortfall |

`coverage` publishes `make coverage`'s page beside them. On the default branch
`verify` and `coverage` also run; on other branches `verify` is manual.

The `libero` runner needs Libero SoC 2024.1 on `PATH`, its QuestaSim, and their
licences. `verify` assembles the inputs that are not in this repository under
`.workspace/` (`FSVERIF_WORKSPACE`, which `fsverif.design.WORKSPACE` reads in
place of this checkout's parent): it clones `farsight-fpga-house-keeper` and
`farsight-avionics-sw` with the job token, and copies the datasheets from
`FSVERIF_DATASHEETS`, a CI/CD variable naming the runner's copy. A missing
input makes the inspections that need it skip, which the gate refuses. The
project must be allowed in the job-token permissions of ts-altium-sch-json and
both sibling repositories.

## 5. Vendor IP

Our IP blocks instantiate Microchip cores -- COREFIFO in the DMA, UDP and
metadata paths, PF_TVS in the temperature monitor -- that Libero generates
from component definitions kept beside the SmartDesigns that use them. The RTL
is Microchip's, so it is **generated, not committed**; what is committed is a
lockfile per component recording what it was generated from.

[`ip.yaml`](ip.yaml) lists the components simulation needs. The build defines
81 vendor components and a block test needs a handful, so only those listed
are generated. `sim.vendor()` refuses one that is not listed. A SmartDesign
entry also names the RTL directories the build links (`sources`) and the IP
scripts it runs first (`prepare`); both are part of the lockfile's digest.

```
make ip                                   # generate what ip.yaml lists
make ip-check                             # is what is here what the design asks for
make ip-import FROM=<other checkout>/verification/ip    # take it from elsewhere, verified
```

**The vault.** Libero generates cores from an IP vault whose location is the
per-user `~/.actel/ipmgr.ini`, shared by every project on the machine. `make
ip` does not read it: Libero runs with `HOME` pointed at a scratch directory
whose `ipmgr.ini` names this checkout's own vault, `.tools/vault`, for that
invocation only. The first `make ip` fills that vault with the cores the
build's `script/common/download.tcl` names, and fills it again when that list
changes; this needs network access to microchip-ip.com. Nothing else writes
to it, and no other vault is read. `make ip LIBERO_VAULT=<vault>` uses an
existing vault as it is, without writing to it.

**Over ssh or anywhere without a display,** Libero exits with "cannot connect to
X server" even in script mode; `make` runs it under `xvfb-run` when that is
installed. `LIBERO_X=` turns this off.

A component generated this way was compared with the same component from a
full build and the source digests are identical, so the scratch project is
not a different core.

## 6. Which simulator

| | Verilator (default) | QuestaSim ME |
| --- | --- | --- |
| our IP blocks | yes | yes |
| soft vendor cores (CoreGPIO, COREFIFO, APB/AHB/AXI fabric, SPI, UART, timers, MIV_RV32) | yes | yes |
| primitives in `polarfire.v` (RAM1K20, RAM64x12, PLL, OSC, INIT, clock mux and divider) | yes | yes |
| encrypted cores: SLVS_EC_RX, CORETSE, PF_DDR4 | **no** | yes, precompiled library |
| hard blocks with no source model: IOD, LANECTRL, DLL, XCVR, PCIE, TX_PLL | **no** | yes, precompiled library |

A DUT that needs the second column pins itself with `sim.run(...,
simulator="questa")`, and only that DUT moves. It does not quietly fall back
to Verilator when QuestaSim is unavailable: running on a simulator that cannot
compile the block would not be the same test. `python -m fsverif.simulators`
reports what this machine can drive. The QuestaSim shipped with Libero SoC
2024.1 is 64-bit and works with cocotb; the bundled ModelSim is 32-bit and
cannot load it.

**Vendor models have delays; sample mid-cycle and reset on an edge.**
Microchip's cores and primitive models drive some outputs after the clock
(`assign #1 MEMRADDR` in COREFIFO; `#1` in the RAM1K20 model). Synthesis
ignores these delays; they are there so an event-driven simulator orders the
behavioural RAM like a real flop. So, for a DUT containing vendor cores:

- **A monitor samples on the falling edge**, not in the read-only phase of the
  rising edge. At the edge a delayed data output still shows the old value
  while an undelayed data-valid shows the new one, so the monitor sees the
  data one word late. What the falling edge sees is what the next rising edge,
  a real consumer, captures. This produced a false one-word shift in the DMA
  write path under both simulators until it was fixed
  (`tests/test_pf_dmaw_rate.py`).
- **Reset is a falling edge** (drive 1, then 0), not 0 from time zero. The
  cores' asynchronous resets act on the edge, and a four-state simulator starts
  the net at X; Verilator's two-state nets hide the difference.
- **Keep `--timing`.** Ignoring the delays (`--no-timing`) happened to give
  the right data here, but it is not what Microchip qualifies the models
  against. When a result depends on a vendor model, QuestaSim with the
  precompiled library is the reference: `SIM=questa`. For COREFIFO-heavy DUTs
  it is also faster.
- **Verilator can misorder the RAM's output register against our RTL.** The
  block RAM's output pipeline register is `SLE_Prim`, a zero-delay flop built
  from sequential UDPs. In the DMA read path, Verilator let `dma_read_ctrl`'s
  input flops sample it *after* the edge, so the controller captured every
  word one word late. The monitor was right; the DUT's own flops were wrong,
  so no sampling choice in the test can fix it. QuestaSim captures correctly,
  so that DUT pins itself to QuestaSim (`tests/test_pf_dmar.py`). A DUT
  whose own RTL consumes a COREFIFO's `Q` should be checked under QuestaSim
  at least once before its Verilator result is trusted.

**A stub is not the block it replaces** (plan, *What this plan does not
establish*). A block-level test with a model standing in at the DDR, camera or
MAC boundary verifies the block against the model; the real vendor block is
exercised where it is present, which for most of it means QuestaSim at
integration level, or hardware.

## 7. Analyses

An analysis item's evidence is its recorded calculation. Here each analysis is
a test function under `verification/analysis/`, run with the simulations by
`make test`. It reads every input from where the build reads it --
SmartDesign parameters, RTL constants, core configurations, flight-software
constants -- through `fsverif.design`, which keeps the file and line each came
from; only requirements' bounds and standards' figures are typed in, and the
record names their source. It then asserts the item's criterion.

Each run writes `results/results-<module>.xml`, read by `make check` and
`make coverage` exactly as a simulation's is, and `results/analysis/<module>.md`,
the calculation as a document. A design change that breaks a budget fails the
analysis the way it would fail a test: no number in a budget can go stale
while the design moves on.

Inspections are written the same way, as `analysis/test_insp_*.py`: each
records what it compared, with the line, and asserts the item's criterion.
Those against the board read the avionics schematic export committed as
`verification/board/CM-03545.json`, through `altium_sch_json`
([ts-altium-sch-json](https://gitlab.com/turionspace/fpga-projects/tools/ts-altium-sch-json),
the reader that ships with the export script, in `requirements.txt`), and the
housekeeper's flight-model pinout (`farsight-fpga-house-keeper`, a sibling
checkout) through `fsverif.board`; without the pinout they skip. An export
the reader finds structurally unsound is refused, not read. A line between the
two FPGAs is checked at both ends, since the schematic names those lines
generically.

**When the schematic changes,** export the released project with the script in
ts-altium-sch-json (its README says how), read the warnings file it writes
beside the export, and replace `board/CM-03545.json` with it, keeping the name.
`.venv-verif/bin/altium-sch-json verification/board/CM-03545.json` prints the
drawing and revision it came from; put that in the commit message. The
committed export is drawing CM-03543 rev 2, exported 2026-10-02 by script
2.6.0, and its netlist is identical to the 2026-09-15 export the inspections
read before it.

## 8. Seeing inside, when a test fails

```
make test TEST=test_pf_pps_local PYTEST_ARGS="-n0 -s"   # live output, one worker
make test TEST=test_pf_pps_local WAVES=1                # a trace file
FSVERIF_VISIBILITY=all make test TEST=...         # every signal addressable, ~10x slower
```

A test that needs one internal signal -- because its item says why -- names it
with `sim.run(..., internal=[("module", "signal")])` rather than opening the
whole design.

Results land in `verification/results/results-<module>.xml`, which is what
`make check` and `make coverage` read.

## 9. What is not there yet

- **Tests.** Every simulation item has its test.
- **Integration level.** Nothing yet simulates the whole design, which needs
  QuestaSim and Libero's precompiled PolarFire library for the encrypted cores
  and hard blocks. `sim.polarfire_questa()` finds that library.
- **The rest of the analyses.** The budgets whose inputs are all in the
  design, the analyses of the retained build's timing, utilisation, clock and
  CDC reports, and every inspection item are in `verification/analysis/`. The
  report analyses skip where there is no retained build under `build/`, and
  fail where the newest one is of other design sources (`fsverif.build`).
  The oscillator budgets and the stepper timing read the parts' figures from
  their datasheets in the workspace's `board-check/datasheets`
  (`fsverif.oscillators`, `fsverif.stepper_driver`, via `pdftotext`) and skip
  without them.
